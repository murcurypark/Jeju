# MedPark 검토 문서 포맷

문서 페이지 이미지 위에 번호 마커와 박스를 올리고, 같은 번호의 메모 카드를 양옆 여백에 두는 **검토용 PPTX**를 만든다. 사용자가 이 포맷을 "깔끔하다"고 확정했다. 한 눈에 "문서의 어디를, 무엇에서 무엇으로, 무엇을 확인해야 하는지"가 보이는 것이 목적이다.

```
┌──────────────┬──────────────────┬──────────────┐
│ 좌측 카드      │  문서 페이지 이미지  │ 우측 카드      │
│ ①②③ (좌단 항목)│  + 빨간/파란 박스 │ ④⑤⑥ (우단 항목)│
└──────────────┴──────────────────┴──────────────┘
```

## 두 가지 버전 (항상 분리한다)

| 버전 | 내용 | 슬라이드 |
|---|---|---|
| **V1 코멘트 반영본** | 사용자가 처음 준 마킹/코멘트만 정리. 확정 사항이라 빨강 카드 | 문서(KO, EN …)당 1장 |
| **V2 추가 검토의견** | 마킹에 없던 Claude 제안·검토의견. 논의용 초안이라 V1과 섞지 않는다 | 문서당 1~2장 (① 문구 수정·정합 / ② 내용 보완·확인) |

V1과 V2를 분리하는 이유: 사용자가 이미 결정한 사항과 Claude가 새로 제안한 사항이 한 장에 섞이면 무엇을 반영해야 하는지 구분이 안 된다.
V2 카드가 한 슬라이드에 8~9개를 넘으면 왼쪽 여백이 넘치므로 "문구 수정·정합"과 "내용 보완·확인"으로 슬라이드를 나눈다. 같은 이미지를 두 번 써도 된다.

## 색 규칙 (cat)

| cat | 색 | 의미 | 주로 쓰는 곳 |
|---|---|---|---|
| `mod` | 빨강 C00000 | 코멘트 반영(확정) | V1 |
| `prop` | 파랑 1F5FBF | 수정 제안(초안) | V2 |
| `chk` | 주황 D26A00 | 확인·보완 필요 | V1의 ※ 줄, V2 |
| `ref` | 회색 6B7280 | 표기·서식 정리 | V2 |

카드 안 줄 종류(`lines`의 첫 값): `old` 현행(회색), `new` 수정/제안, `chk` ※ 확인사항(주황), `txt` 일반 설명.

## 작업 순서

1. **원본 읽기** — 사용자가 준 이미지(마킹본과 깨끗한 원본이 따로 있으면 둘 다)를 읽는다. 마킹된 모든 항목을 빠짐없이 목록으로 만든다. 마킹의 글씨가 흐리면 추측하지 말고 확대해서 읽고, 그래도 불확실하면 카드에 "확인 필요"로 적고 사용자에게 묻는다.
2. **좌표 찾기** — `scripts/make_ruler.py`로 눈금자 이미지를 만들고 Read로 열어 각 강조 대상의 `[x, y, w, h]`(원본 픽셀)를 읽는다. 눈짐작으로 찍으면 박스가 어긋나므로 반드시 눈금자를 쓴다.
3. **spec JSON 작성** — V1용, V2용 두 개. 형식은 아래 "spec 형식" 참조. 카드 문구는 짧게: 한 카드에 현행·수정·확인이 각 1~2줄이면 충분하다.
4. **생성** — `node scripts/build_review_pptx.js spec.json` (pptxgenjs가 없으면 `npm install pptxgenjs`). 이미지는 PNG/JPEG만 받는다(webp는 `make_ruler.py`가 PNG로 변환해 준다).
5. **시각 검증(필수)** — `python3 /mnt/skills/public/pptx/scripts/office/soffice.py --headless --convert-to pdf out.pptx` → `pdftoppm -r 110 -png out.pdf pg` → 이미지를 Read로 열어 확인: 박스가 해당 문구를 정확히 둘러싸는지, 카드가 서로 겹치거나 잘리지 않는지, 하단 각주와 카드가 겹치지 않는지. 어긋나면 spec의 좌표를 고쳐 다시 만든다. (렌더 환경에 맑은 고딕이 없어도 배치 확인에는 충분하다.)
6. **전달** — SendUserFile로 V1·V2 파일을 보내고, 확인이 필요한 사항과 틀렸다고 판명되어 철회한 항목이 있으면 숨기지 말고 알린다.

## spec 형식

```json
{
  "deckTitle": "문서 제목", "out": "V1_코멘트반영본.pptx",
  "slides": [{
    "img": "ko.png",                       // spec 파일 기준 상대경로
    "title": "V1 · 코멘트 반영본 | MedParkAllo IFU (KO) · Rev 0.20 → 0.30",
    "legend": ["mod", "chk"],              // 생략하면 items의 cat에서 자동
    "foot": "...",                         // 생략 시 V2(mod 외 cat이 있을 때)에만 기본 각주, ""면 없음
    "items": [{
      "n": 1, "cat": "mod",
      "side": "L",                         // 생략하면 박스가 이미지 좌/우 어느 단인지로 자동
      "boxes": [[x, y, w, h], ...],        // 원본 픽셀. 첫 박스에 번호 마커+점선 연결, 여러 개 가능, 생략하면 카드만
      "anchorY": 0.5,                      // boxes 없을 때 카드 시작 높이(inch)
      "title": "7.마-1) 일반적 주의",
      "lines": [["old","현행 문구"],["new","수정 문구"],["chk","확인사항"]]
    }]
  }]
}
```
예시는 `assets/example_spec.json`. 카드 높이와 겹침 해소는 스크립트가 자동 처리한다(원하는 높이에 두고, 겹치면 아래로 밀고, 바닥을 넘으면 위로 당김).

## 검토 내용을 만들 때의 원칙 (V2)

이 포맷의 가치는 모양보다 **검토의 정확성**이다. 다음을 지킨다.
- **주장은 확인한 뒤에 쓴다.** 오탈자·수치를 지적하기 전에 해당 부분을 4배 확대해서 다시 읽는다. 저해상도 이미지에서 쉼표/마침표, 받침, 한 글자 누락을 잘못 읽은 적이 있다. 틀린 지적이 발견되면 즉시 철회하고 사용자에게 알린다.
- **KO↔EN 대응을 항목별로 대조한다.** 사용 목적, 제품 설명, 경고·금기·부작용 문구의 강도("~할 수 있다" vs "do not use", "반드시" vs "in conjunction with"), 모델·명칭·제조자·연락처·개정번호까지 본다. 한쪽만 고치면 다른 쪽이 어긋나므로 연동 수정을 V2에 제안한다.
- **허가사항·규정과 연결되는 변경은 "확인 필요"로 표시한다.** 사용 목적, 제품명·모델명, 상호·주소 변경은 허가증/변경허가/사업자등록증과 대조해야 한다. 규정 근거(예: MDR Annex I 23.4(s) 개정일 요건, 국내 표시기재 기준)는 확신이 없으면 "확인 필요"로 쓰고 단정하지 않는다.
- **내용 보완 점검 목록**: 사용 목적 ↔ 경고/주의 문구의 모순, 누락된 사용 절차(이식 방법 등), 권장량·모델별 사양이 IFU 밖 문서에 위임되는지, 부작용 목록이 위험관리 파일의 잔여 위험을 포함하는지, 금기 항목의 통상 누락, 용어 통일(일회용/1회용, 띄어쓰기), 인체유래 제품의 추적성, 표시기재 필수 항목.
- 마킹에 없던 모든 항목은 V2에 둔다(V1에 넣지 않는다). Claude가 쓴 번역·제안 문구는 "초안"임을 각주로 밝힌다.
- 사용자 언어(한국어)와 맑은 고딕, 메드파크 초록(4CB748) 상단 바를 유지한다.

## 번들 파일

- `scripts/build_review_pptx.js` — spec → PPTX 생성 (이미지 크기 자동 인식, 카드 자동 배치)
- `scripts/make_ruler.py` — 좌표 읽기용 눈금자 이미지 + webp→PNG 변환
- `assets/example_spec.json` — spec 예시
